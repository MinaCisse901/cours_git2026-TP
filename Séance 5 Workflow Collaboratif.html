Qu'est-ce qu'un workflow Git ?

Un ensemble de règles et de pratiques pour organiser le travail en équipe

  • Comment créer des branches
  • Quand fusionner dans main
  • Comment gérer les versions et les déploiements

GitHub Flow

Workflow simple et efficace pour petites équipes

  • Une seule branche principale (main)
  • Branches de fonctionnalités courtes
  • Pull Requests pour revue et fusion
  • Déploiement continu depuis main

Étapes du GitHub Flow (1/2)

  1. Créer une branche depuis main
  2. Ajouter des commits
  3. Ouvrir une Pull Request

Étapes du GitHub Flow (2/2)

  1. Revue et discussion
  2. Tester les changements
  3. Fusionner dans main
  4. Supprimer la branche

Qu'est-ce qu'une Pull Request ?

Une demande de fusion de votre branche vers une autre (généralement main)

  • Permet la revue de code avant fusion
  • Espace de discussion sur les changements
  • Documentation de l'historique des décisions

Créer une Pull Request

  1. Pousser votre branche vers GitHub/GitLab
  2. Aller sur la page du dépôt
  3. Cliquer "New Pull Request"
  4. Sélectionner branche source et cible
  5. Rédiger titre et description clairs

Anatomie d'une bonne Pull Request

  • Titre clair : Résume le changement en une ligne
  • Description détaillée : Contexte, motivation, approche
  • Petite taille : 50-200 lignes idéalement
  • Tests ajoutés : Preuve que ça fonctionne

Revue de code (Code Review)

Processus d'examen du code par les pairs avant fusion

  • Détecte les bugs et problèmes potentiels
  • Améliore la qualité du code
  • Partage les connaissances dans l'équipe

Comment faire une bonne revue

  • Lire attentivement les changements
  • Commenter des lignes spécifiques si besoin
  • Être constructif et bienveillant
  • Approuver ou demander des changements

Types de commentaires de revue

  • ✅ Comment : Discussion générale
  • 🔧 Request changes : Modifications nécessaires
  • ✔️ Approve : Changements validés

Merge Request (GitLab)

Équivalent GitLab de la Pull Request GitHub

Fonctionnalités identiques : revue de code, discussion, fusion

Branches locales vs distantes

  • Locale : Sur votre ordinateur uniquement
  • Distante : Sur GitHub/GitLab (origin/feature)
  • Synchroniser avec push et pull

TP Guidé (60 min)

  1. Créer une branche feature, commits, push
  2. Ouvrir une Pull Request sur GitHub/GitLab
  3. Faire une revue de code entre pairs
  4. Fusionner la PR après approbation

Bonnes pratiques : Noms de branches

  • ✅ feature/login-page
  • ✅ bugfix/fix-typo-homepage
  • ✅ hotfix/security-patch
  • ❌ branch1, test, my-branch

Bonnes pratiques : Messages de commit

  • ✅ "Ajouter la page de connexion"
  • ✅ "Corriger bug d'affichage mobile"
  • ❌ "update", "fix", "changes"
  • ❌ "aaaaa", "test123"

Bonnes pratiques : Pull Requests

  • Garder les PR petites (50-200 lignes)
  • Demander au moins 1 revue avant fusion
  • Répondre aux commentaires rapidement
  • Mettre à jour la branche avec main régulièrement

Récapitulatif

  • GitHub Flow = workflow simple et efficace
  • Pull/Merge Requests = revue avant fusion
  • Code review améliore qualité et partage connaissances
  • Bonnes pratiques = noms clairs, petites PR, revues
